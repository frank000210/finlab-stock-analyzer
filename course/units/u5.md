# U5 Multi-Agent：Subagents

> **Agent 原理**：把一個大任務分給多個專責代理，每個代理有自己的指示、工具與 context，最後由主代理彙整。
> **Claude Code 實作**：Subagents（含內建的 Explore、Plan）、skill 預載、`context: fork`。
> **本課實作**：做一個唯讀的 code-reviewer subagent，再用 skill 一次派出多個 subagent 做稽核。

## 為什麼需要多個 Agent

單一 Agent 遇到兩個問題：

1. **Context 被塞爆**：要讀 50 個檔案才能找到答案，這 50 個檔案的內容全部留在 context 裡，後面的工作被雜訊干擾
2. **角色混雜**：同一個 Agent 又要寫程式、又要審程式，很難保持客觀

多代理的解法：**把工作交給一個在獨立 context 裡執行的代理，它做完只回傳摘要**。主對話保持乾淨，專責代理也能有自己的指示與工具限制。

## Subagent 是什麼

Subagent 是一個有自己 context window 的工作者：

- 有**自己的 system prompt**（不是 Claude Code 主對話那份）
- 可以**限制工具**，例如只能讀不能寫
- 可以**指定模型**，例如用便宜的模型做大量搜尋
- 做完之後**只把摘要**交回主對話，中間讀過的檔案、跑過的指令都不會進主對話的 context

Claude 會依照 subagent 的 `description` 自己決定要不要派工，你也可以直接說「用 code-reviewer 看一下這次的修改」。

## 內建的 subagent

| 名稱 | 用途 | 特性 |
|---|---|---|
| Explore | 快速搜尋、分析程式碼 | 唯讀，不能 Write / Edit |
| Plan | plan mode 時蒐集資訊 | 唯讀 |
| general-purpose | 需要探索又要修改的多步驟任務 | 可用全部工具 |

你在 session 裡看到它「派出 Explore 去搜尋」，就是在用 subagent。

## 自訂 subagent

在 `.claude/agents/`（專案）或 `~/.claude/agents/`（個人）放一個 Markdown 檔：

```markdown
---
name: code-reviewer
description: 審查程式碼的品質、安全性與可讀性。寫完或修改程式碼後主動使用。
tools: Read, Grep, Glob
model: sonnet
---

你是資深的程式碼審查員。針對指定的修改：

1. 先用 `git diff` 的結果了解改了什麼（若主代理已提供 diff 就直接使用）
2. 依序檢查：正確性 → 安全性 → 可讀性 → 測試
3. 每個問題標出檔案與行號，說明風險，並給出具體修改建議
4. 沒有問題的面向就說沒有問題，不要硬湊

最後用一段話總結：可以合併／需要修改後再合併。
```

### 常用欄位

| 欄位 | 作用 |
|---|---|
| `name`（必填） | 唯一名稱 |
| `description`（必填） | 何時派工給它，Claude 據此判斷 |
| `tools` | 允許使用的工具清單；省略則繼承主對話的工具 |
| `disallowedTools` | 要移除的工具 |
| `model` | `sonnet`、`opus`、`haiku`、`inherit` 或完整模型 ID |
| `skills` | 啟動時就預先載入完整內容的 skill |
| `permissionMode` | 這個 subagent 的權限模式 |
| `memory` | `user`、`project` 或 `local`，讓它有跨 session 的記憶 |

上面的 code-reviewer 只給了 `Read, Grep, Glob`——**它根本沒有寫檔的能力**。這比在提示詞裡寫「請不要修改檔案」可靠得多。

輸入 `/agents` 可以請 Claude 幫你建立或編輯 subagent。同名時的優先順序：組織 > `--agents` 命令列參數 > 專案 > 個人 > plugin。

## Subagent 看到什麼

這是最常踩的坑：**一般的 subagent 看不到你和主代理的對話**。它啟動時有：

- 它自己的 system prompt（定義檔的內文）
- `skills` 欄位列出的 skill 全文
- CLAUDE.md 與 git 狀態（內建的 Explore、Plan 沒有）
- 主代理派工時寫給它的任務說明

所以主代理派工時必須把背景交代清楚。你自己寫 subagent 的指示時，也要假設它「什麼都不知道」。

例外是 **fork**：fork 會複製目前整段對話給它，適合需要大量前情的支線任務。

## Skill 與 subagent 的組合

### 讓 skill 在 subagent 裡執行

在 skill 的 frontmatter 加上：

```yaml
context: fork
agent: Explore
```

這個 skill 被呼叫時，就會在獨立的 subagent 中執行，主對話只收到結果。適合「要讀很多東西、但只需要結論」的 skill。注意 skill 內容必須自給自足——subagent 看不到你的對話。

### 用 skill 一次派出多個 subagent

```markdown
---
name: audit
description: 對指定目錄做全面稽核
disable-model-invocation: true
---

對 $ARGUMENTS 平行派出三個 subagent，各自獨立檢查並回報：
1. 安全性：注入、權限、機密外洩
2. 效能：N+1 查詢、不必要的迴圈、缺少快取
3. 可維護性：重複程式碼、過長函式、缺少測試

全部回來後，合併成一份依嚴重程度排序的報告。
```

## 什麼時候用、什麼時候不用

| 情況 | 建議 |
|---|---|
| 要讀很多檔案、只需要結論 | ✅ subagent |
| 平行的獨立工作（三個面向的稽核） | ✅ 多個 subagent |
| 需要不同的工具限制或角色（唯讀審查） | ✅ 自訂 subagent |
| 很小的任務，一兩個工具呼叫就完成 | ❌ 直接做，派工反而多花時間 |
| 需要跟你來回討論細節 | ❌ 在主對話做 |
| 工作量大到需要幾十個代理、還要交叉驗證 | 考慮 dynamic workflow |

## 本課小結

- Subagent 的核心價值是 **context 隔離**：做很多事、只交回摘要
- 用 `tools` 限制能力，比提示詞裡的「請不要」可靠
- 一般 subagent 看不到你的對話，派工時要交代清楚
- `context: fork` 讓 skill 在 subagent 中執行；skill 也可以派出多個 subagent
