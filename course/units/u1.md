# U1 LLM 與 Prompt 基礎

> **Agent 原理**：模型每次回應時，只看得到 context window 裡的東西。
> **Claude Code 實作**：CLAUDE.md、`.claude/rules/`、output style、`/context`。
> **本課實作**：為一個專案寫出好的 CLAUDE.md，並做一個自訂 output style。

## Context window：Agent 唯一的工作記憶

大型語言模型（LLM）沒有「記住」這回事。每一次呼叫，模型都是讀一大段文字（context）然後產生下一段回應。對 Agent 來說，這段 context 包含：

- **System prompt**：工具開發者寫好的基本指示（Claude Code 自己的那份）
- **你的指示檔**：CLAUDE.md、rules、output style
- **工具定義**：它能用哪些工具
- **對話歷史**：你說的話、它讀過的檔案內容、執行過的指令輸出

Context 有上限，而且每一個 token 都要花錢、花時間。更重要的是：**塞太多不相關的東西，模型反而容易忽略重要的指示**。

在 Claude Code 裡輸入 `/context`，可以看到目前 context 被哪些類別佔用。養成習慣：覺得它「變笨」或「忘記規則」時，先看一下 `/context`。

當 context 快滿時，Claude Code 會自動壓縮（先清掉舊的工具輸出，必要時摘要整段對話）。壓縮後，**對話早期講過的細節可能會遺失**——所以長期有效的規則不要只在對話裡講，要寫進 CLAUDE.md。

## CLAUDE.md：每次都載入的專案說明

CLAUDE.md 是一個 Markdown 檔，**每個 session 開始時自動載入 context**。適合放「每次都該知道」的事：

- 建置與測試指令（「用 `npm test` 跑測試」）
- 程式碼慣例（「縮排用 2 個空格」）
- 專案結構（「API handler 放在 `src/api/handlers/`」）
- 絕對禁止的事（「不要直接改 `migrations/` 裡已經上線的檔案」）

### 放在哪裡

| 層級 | 位置 | 誰看得到 |
|---|---|---|
| 組織 | 系統管理員部署的路徑（Windows 是 `C:\Program Files\ClaudeCode\CLAUDE.md`） | 組織內所有人 |
| 個人 | `~/.claude/CLAUDE.md` | 只有你，所有專案 |
| 專案 | `./CLAUDE.md` 或 `./.claude/CLAUDE.md` | 進版控，整個團隊 |
| 本機 | `./CLAUDE.local.md`（加進 .gitignore） | 只有你，這個專案 |

這些檔案是**疊加**的，不是覆蓋：全部一起放進 context，越接近工作目錄的越晚被讀到。子目錄裡的 CLAUDE.md 會在 Claude 讀寫該目錄的檔案時才載入。

### 匯入其他檔案

在 CLAUDE.md 裡寫 `@路徑` 可以把別的檔案一起帶進來，例如：

```markdown
專案概覽見 @README.md，可用的 npm 指令見 @package.json。
```

注意：匯入只是讓檔案好整理，**不會省 context**——被匯入的檔案會跟著一起載入。

## 寫出有效的指示

官方的建議很明確：**具體到可以驗證**。

| ❌ 模糊 | ✅ 具體 |
|---|---|
| 程式碼要整齊 | 縮排用 2 個空格，字串用單引號 |
| 改完要測試 | commit 前執行 `npm test`，全部通過才 commit |
| 檔案要分類好 | API handler 放在 `src/api/handlers/` |

另外三個原則：

1. **每個檔案控制在 200 行內**。太長會吃 context，遵循度反而下降
2. **用標題和條列整理**，比一大段文字好遵循
3. **定期清掉矛盾的規則**。兩條規則互相衝突時，模型可能隨機挑一條。可以用 `/doctor prompt-audit` 讓它幫你找

一個好用的經驗法則：**同一個錯誤它犯了兩次，就把正確做法寫進 CLAUDE.md**。

## 用 rules 拆分規則

專案大了，CLAUDE.md 會越來越長。這時可以把規則拆到 `.claude/rules/` 底下，每個主題一個檔案。

更好用的是 **路徑限定規則**：在 frontmatter 寫 `paths`，只有在 Claude 處理符合的檔案時才載入：

```markdown
---
paths:
  - "src/api/**/*.ts"
---

# API 開發規則
- 每個 endpoint 都要有輸入驗證
- 錯誤回應統一用 { error: string } 格式
```

這樣寫前端時，API 規則就不會佔用 context。

## Output style：改變回應的方式

CLAUDE.md 管的是「**它該知道什麼**」，output style 管的是「**它怎麼回應你**」——語氣、長度、格式、角色。

內建的 style：

| Style | 效果 |
|---|---|
| Default | 標準的軟體工程助手 |
| Proactive | 遇到例行決定直接做，不停下來問 |
| Concise | 先講結果，省略開場白與總結 |
| Explanatory | 額外加上 `Insight` 區塊解釋為什麼這樣寫 |
| Learning | 除了解釋，還會留幾段程式讓你自己寫（標 `TODO(human)`） |

切換方式：輸入 `/output-style concise`，或在設定檔寫 `"outputStyle": "Concise"`（設定檔裡大小寫要完全一致）。

### 自訂 style

在 `.claude/output-styles/`（專案）或 `~/.claude/output-styles/`（個人）放一個 Markdown 檔：

```markdown
---
name: 教練模式
description: 用教學的方式回答，先講概念再給做法
keep-coding-instructions: true
---

回答時先用一句話說明背後的概念，再給具體步驟。
遇到我可能不懂的名詞，第一次出現時附上英文原名與一句解釋。
```

`keep-coding-instructions: true` 代表保留 Claude Code 原本的軟體工程指示；如果你要它變成完全不同的角色（例如寫作助手），就不要加。

## CLAUDE.md 與 output style 怎麼選

| 你想要的 | 用什麼 |
|---|---|
| 專案事實、指令、慣例 | CLAUDE.md |
| 只跟某些檔案有關的規則 | `.claude/rules/` + `paths` |
| 回應的語氣、長度、格式 | Output style |
| **一定要做到、不能有例外的事** | **Hook（U6）** |

最後一列非常重要：CLAUDE.md 和 output style 都只是「指示」，模型會盡量遵守，但**不保證**。要強制的規則，請等 U6 學 hook。

## 本課小結

- 模型只看得到 context 裡的東西；context 有成本，也有雜訊問題
- CLAUDE.md 每次都載入，寫「具體、可驗證、200 行內」的指示
- 用 `.claude/rules/` + `paths` 讓規則只在需要時載入
- Output style 改變回應方式，不是改變專案知識
- 指示是請求，不是保證
