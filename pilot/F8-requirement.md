# F8 可執行需求：持有期處置效應偵測器

> 這份文件是「pilot：需求→實作→整合測試閉環」的需求物件。
> 它示範一份**agent 看得懂、且成功與否可被客觀裁判**的需求該長什麼樣。
> 對應公司場景：這就是未來要訓練 PM 寫的「可執行需求」範本。

## 1. 背景與動機（給 agent 的 context）

`複盤教練`（`frontend/src/views/JournalView.vue` 的 `coachInsights`）目前有 11 條規則式紀律建議。
本需求新增第 12 條：偵測「**處置效應**」——交易者傾向**太快了結獲利、卻抱著虧損不放**，
是長期侵蝕期望值的典型行為偏誤。

## 2. 明確驗收條件（= 裁判，不可含糊）

新增一個 computed `holdingDisposition`，並在 `coachInsights` 加入對應規則：

- **資料來源**：`closedTrades`（已平倉交易），持有天數 = `round(exitDate - openDate)`（日）。
- **觸發樣本門檻**：獲利交易 ≥ 3 筆 **且** 虧損交易 ≥ 3 筆（樣本不足時回傳 `null`，不顯示，避免雜訊）。
- **觸發條件**：`虧損交易平均持有天數 / 獲利交易平均持有天數 >= 1.5`。
- **顯示內容**：`tone: 'bad'`，文字須**同時包含**：
  - 虧損平均持有天數（整數）+「天」
  - 獲利平均持有天數（整數）+「天」
  - 關鍵詞「**砍贏單**」與「**處置效應**」
- **不觸發**：當持有天數比值 < 1.5（贏賠抱單時間相當）時，該條建議**不得出現**。

## 3. 非目標（防止與現有規則重疊）

- 不處理「盤中時間鄰近性的報復性交易」——資料模型無盤中時間戳，算不出來。
- 不重複「連續虧損」（規則 3）與「單日爆量」（規則 9）已涵蓋的角度。
- 純前端、不打任何 API（與 F3~F7 一致，交易資料存 `localStorage`）。

## 4. 執行合約（integration test = oracle）

驗收測試：`e2e/tests/journal-holding-disposition.spec.js`（先寫、且一開始必須是紅燈）。
實作完成的定義：該測試轉綠 **且** 既有 31 支 e2e 測試無一被打壞。
